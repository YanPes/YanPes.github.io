## Introduction

you propably only get this opportunity once in a career. a large enterprise e-commerce platform serving to customers in over 55 countries with immensely large annual turnover and a crazy amount of daily traffic generated around the globe. the project is already quite old about 10 years. naturally the tech stack was quite dusty as well - solid but dusty - still rocking good old Java Spring MVC with XML (not even boot) and the trustworthy JSP server side html outlet. On top of that the good old jQuery and SASS on frontend with a custom implementation of mounting react components or modules to enhance the customer journey. After all these years the system needed to be reinvented. so lets think big right? first thing that comes to your mind? totally correct - split backend from frontend with clean, manageable and scalable REST interfaces to clean up the hard coupling between backend and frontend development. good start. but thats not all. the platform landscap consistet of several application teams providing components, modules or pages on top of the already extensive system. how were they integrated? You guessed it - Good old iframes and nasty javascript injection without any control on the host system side. so we ring the bell for the second round and we start the fight against the monolithic structures that generated dependencies like hell and throttled teams left and right because of bottlenecks, as every team works decentral in different locations, countries, schedules, work modes and so on. what's the solution? after careful architectural consideration and several ADRs and revisions on the architecture concept we decided to go with a microfrontend architecture supported by Module Federation. As this new mental shift on the way the web works (mindblowing if you experience it for the first time I promise - it feels like the web decomposes to lego blicks you can assemble and be creative as you have been in your childhood.). What is the easiest way of entry? lets start by slicing the elephant into big semantic chunks to split the customer journey in a meaningful way without creating too many modules at once leading to mass chaos and trouble in infrastrucrure, scaling and devops later on. Lets stick to a polyrepo approach as it is the easiest abstraction to keep teams nice isolated and easier to handle. so much for the introduction. i will not go into details on the actual migration and pitfalls, issues, learning curves and so on as this will occupy several blog articles. this time lets focus on Nx monorepositories. after the poly repo approach did work out for a lot of applications we soon ran into orchestration issues. creating new modules and applications was more tedious the more code and complexity arrived at the system. more chore on every system scaling increment. a new branching model brought so much confusion to the dev teams that issues and bug accumulated like crazy. but not just technical dept accumulated. shared libraries hosted on artifactory were a chore to update as well as to keep in sync. it felt like the more the new architecture was building up, all the nice benefits of a decentralized architecture began to vanish because of overhead work that needed to be done. updating libs in package.json files over 20 applications? create a script for it. ouch i still feel the pain.
So what to do? Well Monorepository was something i wanted to have since all the way at the start. The idea was set on hold as devops collegues and infra colleuges told me it is too complex and big of a change on that scale. after feeling all this pain me and a good collegue went in the pain cave and went all in nerd mode and bonked the whole system to a monorepository incl. frontend changes, CI changes, infrastructure changes, hosting adaptions, monitoring and operations changes, library migrations, pipeline adaptions, generation of resilient and scalable tooling with Nx for more developer experience, extensive config alignments. all in all it was a PR consisting of multiple thousand lines of code and Yes, this was before Codex and Claude. Handcrafted, painstaking migration of a system that was going in the wrong direction. 
was is worth it? yes definitely. the devs are happy now. clean boundaries. clean repository structures. working codeowner files to separate responsibilites, no npm packges to share static code, easy testing orchestration ... the list goes on forever.
